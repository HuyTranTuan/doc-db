Bức Tranh Tổng Thể: Khi nào dùng Database nào?

Không có Database nào là hoàn hảo nhất, chỉ có sự lựa chọn phù hợp nhất cho dự án của bạn. Việc hiểu rõ điểm mạnh yếu giúp bạn thiết kế hệ thống bền vững ngay từ đầu.

Đặc điểm MySQL PostgreSQL SQL Server MongoDB
Loại CSDL Relational (SQL) Relational / Object-Relational Relational (SQL) NoSQL (Document)
Điểm mạnh tuyệt đối Phổ biến, nhẹ, dễ cài đặt. Đọc (Read) siêu nhanh. Hệ sinh thái khổng lồ (PHP/Laravel). "Oracle mã nguồn mở". Chuẩn SQL khắt khe, hỗ trợ JSON cực xịn (đánh index được), xử lý không gian (PostGIS). Hệ sinh thái Microsoft đỉnh cao. Tool quản trị SSMS vô địch. Tối ưu cực tốt cho Windows/C#. Schema-less (không gò bó cột). Scale ngang dễ dàng. Lưu trữ data dạng JSON, phù hợp crawl data, log.
Điểm yếu Query phức tạp (Analytical/Window functions) kém hơn Postgres. Thiếu full-outer-join. Cấu hình tuning ban đầu khá phức tạp. Ngốn RAM hơn MySQL với các kết nối lớn. Tốn phí bản quyền rất đắt (bản Enterprise). Chạy trên Linux chưa thật sự hoàn hảo 100%. Data dễ bị "rác" nếu dev không quản lý code tốt. JOIN (Lookup) cực kỳ tốn tài nguyên.
Dự án phù hợp Web eCommerce, CMS (WordPress), App cơ bản. Hệ thống tài chính, ERP, App dùng lẫn lộn SQL và JSON, App bản đồ. Hệ thống doanh nghiệp lớn, nội bộ công ty dùng stack .NET. Mạng xã hội, Hệ thống phân tích log, Giỏ hàng thương mại điện tử, Data thay đổi liên tục.

MySQL: Nhanh, Phổ biến, Quốc dân

Database mà 90% web developer đều học đầu tiên. Nếu bạn không biết chọn DB nào, MySQL luôn là lựa chọn an toàn. Sử dụng Storage Engine InnoDB (Mặc định).

# Lệnh Cốt Lõi & Đọc Hiểu EXPLAIN

// 1. Khởi tạo & Thao tác cấu trúc (DDL)
CREATE TABLE users (
    id INT AUTO_INCREMENT PRIMARY KEY,
    email VARCHAR(255) NOT NULL UNIQUE,
    status ENUM('active', 'banned') DEFAULT 'active',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- Thêm 1 cột (ALTER)

INSERT INTO product_views (product_id, view_count) 
VALUES (1, 1)
ON DUPLICATE KEY UPDATE view_count = view_count + 1;

🔍 Chiến lược Thực thi (EXPLAIN) - Đọc bệnh chậm query

Thêm từ khóa EXPLAIN trước lệnh SELECT để xem MySQL quét dữ liệu ra sao thay vì trả về kết quả.

EXPLAIN SELECT * FROM orders WHERE user_id = 5 AND status = 'pending';

Các cột quan trọng cần nhìn trong kết quả EXPLAIN:

  • type: Cách lấy data.
    👉 ALL (CỰC TỆ - Quét toàn bộ bảng từ đầu tới cuối).
    👉 range (Tạm ổn - Quét 1 khoảng index, vd: BETWEEN).
    👉 ref / eq_ref / const (TUYỆT VỜI - Truy cập trực tiếp qua Index).
  • possible_keys: Các Index có thể dùng.
  • key: Index THỰC SỰ được MySQL đem ra xài. (Nếu bằng NULL thì lo tạo Index đi).
  • rows: Ước tính số dòng phải quét để tìm ra kết quả (càng nhỏ càng tốt).
  • Extra: Using filesort hoặc Using temporary là điềm xấu, báo hiệu câu ORDER BY/GROUP BY đang làm DB sặc tiết.

# Quản trị, Phân quyền & Backup

// Tạo User & Phân quyền
-- Tạo user chỉ kết nối được từ localhost
CREATE USER 'backend_dev'@'localhost' IDENTIFIED BY 'matkhau123';

-- Cấp quyền Đọc/Ghi/Sửa/Xóa riêng cho DB my_app
GRANT SELECT, INSERT, UPDATE, DELETE ON my_app.* TO 'backend_dev'@'localhost';

-- Cập nhật quyền vào hệ thống
FLUSH PRIVILEGES;
# Lệnh Terminal (Không phải SQL) - Backup DB
# Dump (Xuất) Database ra file .sql
mysqldump -u root -p my_app > backup_myapp.sql

# Dump lấy Cấu trúc bảng (Bỏ qua data)
mysqldump -u root -p --no-data my_app > schema.sql

# Restore (Phục hồi) từ file
mysql -u root -p my_app < backup_myapp.sql

PostgreSQL: Vua Mã Nguồn Mở

Trâu bò, chuẩn mực, nhiều tính năng xịn như JSONB, Array, Window Functions. Rất phù hợp cho các bài toán phân tích dữ liệu, Data Warehouse hoặc ứng dụng lưu trữ linh hoạt hỗn hợp.

# Các tính năng "Sát thủ" (JSON, Array, CTE)

1. Thao tác với JSONB (Siêu tốc độ)

Postgres có thể làm NoSQL! Khác với JSON thường (chỉ là chuỗi), JSONB lưu dưới dạng nhị phân, cho phép truy vấn và tạo Index bên trong JSON.

CREATE TABLE logs ( id SERIAL PRIMARY KEY, data JSONB );

-- Tìm các row có `data` chứa {"status": "error"}
SELECT * FROM logs WHERE data @> '{"status": "error"}';

-- Lấy ra 1 field trong JSONB (Dùng ->> trả về text)
SELECT data->>'user_agent' AS browser FROM logs;

-- Đánh Index GIN (Cực xịn) cho JSONB để search siêu nhanh
CREATE INDEX idx_logs_data ON logs USING GIN (data);

2. Cột dạng Mảng (Array)

CREATE TABLE posts ( tags TEXT[] );
INSERT INTO posts VALUES (ARRAY['Tech', 'Database']);

-- Tìm bài viết có tag 'Tech' (Dùng toán tử ANY)
SELECT * FROM posts WHERE 'Tech' = ANY(tags);

3. Window Functions (Dùng làm báo cáo cực đỉnh)

Không gộp dòng lại như GROUP BY. Nó vẫn giữ nguyên số dòng nhưng thêm cột tính toán.

-- Xếp hạng nhân viên theo lương trong TỪNG PHÒNG BAN (Partition By)
SELECT name, department, salary,
       RANK() OVER (PARTITION BY department ORDER BY salary DESC) as rank
FROM employees;

# EXPLAIN ANALYZE & Quản trị Postgres

EXPLAIN ANALYZE

Khác với MySQL chỉ EXPLAIN (chỉ đoán), thêm ANALYZE trong Postgres sẽ **chạy thật** câu lệnh để đo thời gian thực tế.

EXPLAIN ANALYZE SELECT * FROM users WHERE age > 30;
  • Seq Scan: Quét tuần tự cả bảng (Giống ALL của MySQL).
  • Index Scan: Tìm qua Index (Tốt).
  • Index Only Scan: Siêu nhanh. Dữ liệu cần thiết lấy luôn từ Index, không thèm ngó vào Bảng chính nữa.

# T-SQL & Cú pháp đặc thù

-- 1. Không dùng LIMIT, dùng TOP
SELECT TOP 10 * FROM Customers ORDER BY Score DESC;

-- 2. Khai báo biến và logic rẽ nhánh (IF ELSE) ngay trong script SQL
DECLARE @UserId INT = 5;
IF EXISTS(SELECT 1 FROM Users WHERE Id = @UserId)

    PRINT 'User exists';
END

-- 3. Xử lý NULL (ISNULL thay vì IFNULL của MySQL)

# CTE, Stored Procedure & Tính hiệu năng

CTE (Common Table Expressions)

Tạo ra 1 bảng tạm thời trên Ram để tái sử dụng trong câu query. Giúp code gọn, thay thế cho Sub-query lòng vòng.

WITH Sales_CTE AS (
  SELECT UserId, SUM(Total) AS TotalSales
  FROM Orders GROUP BY UserId
)
-- Sử dụng bảng ảo vừa tạo
SELECT u.Name, s.TotalSales 
FROM Users u 
JOIN Sales_CTE s ON u.Id = s.UserId;

Đo hiệu năng trực tiếp

SQL Server Management Studio (SSMS) có nút Include Actual Execution Plan (Ctrl+M) xem bằng sơ đồ. Nhưng bằng code, bật cái này:

SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT * FROM Users WHERE Username = 'admin';
-- Sau khi chạy sẽ in ra TAB Messages:
-- Dòng "logical reads" càng cao -> Query càng lởm.
-- Quét RAM (logical read) nhiều làm nghẽn cổ chai.

MongoDB: Kẻ phá vỡ rào cản Cột/Bảng

Database NoSQL hướng tài liệu (Document). Lưu dữ liệu y chang cấu trúc JSON/Object của Code. Cực phù hợp cho start-up làm app thay đổi tính năng xoành xoạch mà ko muốn ALTER TABLE mất công.

# Từ điển đối chiếu & Cú pháp CRUD

Table = Collection Row = Document Join = $lookup 
// 1. Tìm kiếm (Giống SELECT WHERE)
db.users.find({ age: { $gte: 18, $lte: 30 } }); // >= 18 và <= 30

// 2. Cập nhật. RẤT QUAN TRỌNG: Phải dùng $set. Nếu không nó ghi đè mất luôn doc!
db.users.updateOne(
  { _id: 1 }, 
  { $set: { name: "Bob" }, $inc: { view: 1 } } // $inc: tăng view lên 1
);

// 3. Xử lý Mảng bên trong Document (Thêm sở thích)
db.users.updateOne({ _id: 1 }, { $push: { hobbies: "Coding" } });

# Aggregation Pipeline (Đường ống ma thuật)

Mọi thứ phức tạp như GROUP BY, JOIN, FILTER trong SQL sẽ được giải quyết bằng "Đường ống" theo từng giai đoạn (Stage). Data đi qua stage 1 bị bóp nhỏ lại, đổ xuống stage 2 xử lý tiếp...

db.orders.aggregate([
  // Giai đoạn 1: Lọc (Giống WHERE) - Chỉ lấy đơn hàng đã giao
  { $match: { status: "delivered" } },

  // Giai đoạn 2: Kéo data từ bảng khác vào (Giống LEFT JOIN)
  { $lookup: {
      from: "users",        // Tên collection muốn join
      localField: "userId", // Cột ở bảng orders
      foreignField: "_id",  // Cột ở bảng users
      as: "user_info"       // Tên mảng kết quả trả về
  }},

  // Giai đoạn 3: Gom nhóm (Giống GROUP BY) - Tính tổng tiền theo ngày
  { $group: {
      _id: "$date",
      totalRevenue: { $sum: "$amount" }
  }},

  // Giai đoạn 4: Sắp xếp (Giống ORDER BY DESC)
  { $sort: { totalRevenue: -1 } }
]);

# 11. Nâng cao: Lệnh TRUNCATE & 3 Lỗi Gây Chậm DB

// Khái niệm nâng cao: DROP vs TRUNCATE vs DELETE

-- 1. DELETE (DML - Chậm nhất, An toàn nhất)
DELETE FROM orders WHERE status = 'cancelled'; 
-- Quét từng dòng, khóa (lock) từng dòng, ghi log từng dòng để có thể Undo (Rollback). Cột ID tự tăng KHÔNG bị reset. Xóa 10 triệu dòng có thể làm treo DB.

-- 2. TRUNCATE (DDL - Siêu tốc độ, Cực kỳ nguy hiểm)
TRUNCATE TABLE orders;
-- Chạy trong 1s dù bảng có 1 tỷ dòng. Vì nó ném luôn file lưu trữ bảng đó đi ở cấp hệ điều hành và tạo 1 bảng trống y hệt. KHÔNG ghi log, KHÔNG thể Rollback, RESET luôn cột ID tự tăng về 1.

-- 3. DROP (DDL - Hủy diệt)
DROP TABLE orders;
-- Xóa sạch sành sanh từ Data đến Cấu trúc bảng (Schema). Mất luôn cái bảng.

1. Lỗi Index (Quên đánh, Composite, Covering)

Định luật: Cột nào hay xuất hiện sau WHERE, ORDER BY, JOIN ON thì phải tạo Index cho nó.
Composite Index (Index gộp): CREATE INDEX idx_user ON users(status, created_at). CHÚ Ý: Luật "Left-most prefix" (Phải dùng từ trái sang phải). Nếu bạn `WHERE created_at = ?` mà không có `status`, DB sẽ KHÔNG dùng index này.
Covering Index: Nếu bạn `SELECT status, created_at` và 2 cột này đã nằm trong Composite Index, DB sẽ lấy data trực tiếp từ cây B-Tree Index trả về luôn mà không thèm chọc vào bảng thật, tốc độ bàn thờ.

2. Lỗi Khóa (Lock) và Deadlock do Transaction

Biểu hiện: CPU bình thường nhưng Query chạy tốn vài chục giây. Khả năng cao do các Query đang tranh giành quyền Ghi (Write Lock) trên cùng 1 dòng dữ liệu.
Isolation Level (Mức độ cô lập): Mặc định MySQL là Repeatable Read, nó sẽ khóa (Lock) dữ liệu gắt gao hơn để chống đọc sai. Nếu app của bạn chỉ cần đọc nhanh không quan trọng dữ liệu vừa bị thằng khác sửa cách đây 1s (vd: đếm view, like), hãy cân nhắc hạ xuống Read Committed để giảm thiểu Lock hãm tốc độ.

3. Phân trang LIMIT/OFFSET mù quáng (Trang quá sâu)

Lệnh LIMIT 10 OFFSET 1000000: Máy chủ phải lật qua ĐÚNG 1 TRIỆU record đầu tiên, vứt đi, rồi lấy 10 record tiếp theo. Cực kì ngốn CPU (Lỗi phổ biến nhất khi làm API list).
Khắc phục: Dùng Keyset Pagination (Cursor). Client gửi ID cuối cùng của trang trước. Câu query trở thành: WHERE id > 1000000 LIMIT 10. Database chọc thẳng vào ID 1000000 trong Index lấy luôn, mất đúng 1ms.

Redis: Phép thuật In-Memory Cache

Thay vì lúc nào cũng chọc vào Database vật lý (ổ cứng HDD/SSD) rất chậm, ta lưu tạm kết quả lên RAM (Redis). Tốc độ trả về gần như 0ms.

# Vận hành chuyên sâu: Lưu trữ, Phân trang & Tìm kiếm

Redis Lưu Data ra sao? (RDB vs AOF)

Redis lưu trên RAM, nếu cúp điện thì mất hết? KHÔNG! Redis có cơ chế ghi xuống ổ cứng (Persistence):

  • RDB (Snapshot): Cứ 5 phút chụp hình RAM 1 lần lưu thành file `dump.rdb`. Phục hồi siêu nhanh, nhưng nếu sập ở phút thứ 4 thì mất data 4 phút đó.
  • AOF (Append Only File): Bạn gõ lệnh gì (`SET a 1`), nó ghi dòng lệnh đó vào file text. An toàn tuyệt đối (không mất data), nhưng file sẽ rất to và phục hồi chậm.
  • Best Practice: Bật cả 2. Hoặc cấu hình chạy RDB, còn AOF chỉ ghi mỗi giây 1 lần (fsync everysec).

Chiến lược dọn rác (Eviction Policy)

RAM thì có hạn (vd server 2GB). Khi RAM đầy, Redis sẽ làm gì với Data mới đưa vào?

  • allkeys-lru: Xóa các Key ít được sử dụng nhất trong thời gian dài (Chiến lược phổ biến nhất để làm Cache).
  • allkeys-lfu: Xóa các Key có tần suất truy cập thấp nhất.
  • noeviction: Không xóa gì cả, RAM đầy thì báo lỗi OOM (Out of Memory). Dùng khi Redis đóng vai trò là DB chính chứ không phải Cache.

// Kỹ thuật Phân trang (Pagination) bằng Redis (Siêu cấp)

Thay vì Cache cả cục JSON bự chảng cho Page 1, Page 2... Rất dễ lỗi thời khi Data đổi. Ta dùng ZSET lưu ID, và HASH lưu Data riêng lẻ.

-- BƯỚC 1: Lưu dữ liệu từng bài viết vào HASH (Key: "post:{id}")
HSET post:101 title "Redis xịn" author "Alex"
HSET post:102 title "Học Postgres" author "Bob"

-- BƯỚC 2: Thêm ID bài viết vào 1 danh sách ZSET. Cột ĐIỂM (Score) chính là Timestamp để sắp xếp mới nhất
ZADD posts:timeline 1700000000 "101" 1700005000 "102"

-- BƯỚC 3: Xử lý Request Lấy Page 1 (10 bài mới nhất)
-- Dùng ZREVRANGE lấy 10 cái ID từ trên xuống (Offset 0, Limit 10)
ZREVRANGE posts:timeline 0 9
-- Trả về: ["102", "101"]

-- BƯỚC 4: Code Backend lấy mảng ID đó, vòng lặp gọi HMGET để lấy thông tin chi tiết
HMGET post:102 title author

🔍 Tìm kiếm trên Redis (Search)

Bản thân Redis nguyên thủy là dạng Key-Value, nó KHÔNG sinh ra để gõ chữ "Re" tìm ra "Redis" (LIKE %..%). Để tìm kiếm, bạn có 2 cách:

  • Cách 1 (Thủ công bằng SET): Tạo các tập hợp (Set). Ví dụ:
    SADD tag:tech "post:1" "post:2"
    SADD tag:new "post:2" "post:3"
    Để tìm bài viết vừa có tag `tech` VÀ `new`, dùng phép giao: SINTER tag:tech tag:new -> Kết quả ra post:2.
  • Cách 2 (Siêu vũ khí RediSearch): Phải cài thêm Module (hoặc xài Redis Stack). Nó biến Redis thành 1 Engine tìm kiếm Full-text xịn như ElasticSearch.
    FT.CREATE idx:posts ON HASH PREFIX 1 post: SCHEMA title TEXT author TAG
    FT.SEARCH idx:posts "@title:Redis @author:{Alex}"

Graph Database (Neo4j): Mạng lưới các mối quan hệ

Khi dự án của bạn đụng tới "Mạng xã hội", "Gợi ý sản phẩm", "Tìm đường đi ngắn nhất", việc dùng bảng SQL (JOIN qua lại hàng chục lần) sẽ khiến hệ thống chết tắc. Graph DB sinh ra để làm việc này.

# Tư duy đồ thị & Ngôn ngữ Cypher

Graph DB vứt bỏ hoàn toàn khái niệm Bảng/Cột. Nó chỉ có 2 thứ: Node (Nút - Thực thể) và Edge/Relationship (Cạnh - Mối quan hệ). Cả 2 đều có thể chứa Properties (Thuộc tính).

(Node: Person {name: 'A'})
-[:KNOWS]->
(Node: Person {name: 'B'})

// Truy vấn Cypher (Neo4j) - Vẽ hình bằng Text

-- 1. Tạo 2 người và mối quan hệ Bạn Bè
CREATE (a:Person {name: 'Alice'})
CREATE (b:Person {name: 'Bob'})
CREATE (a)-[:FRIEND_WITH {since: 2023}]->(b)

-- 2. Đỉnh cao: Thuật toán Hệ thống gợi ý kết bạn (Recommendation) - Chỉ bằng 2 dòng code
-- "Tìm bạn của bạn của Alice, nhưng người đó CHƯA LÀ bạn trực tiếp của Alice"
MATCH (alice:Person {name: 'Alice'})-[:FRIEND_WITH]->(friend)-[:FRIEND_WITH]->(fof)
WHERE NOT (alice)-[:FRIEND_WITH]->(fof)
RETURN fof.name;

Giám Sát (Monitoring): Prometheus & Grafana

Bộ đôi thần thánh để theo dõi sức khỏe của Database và Server. Prometheus có nhiệm vụ đi "hút" dữ liệu (pull metrics), Grafana lấy dữ liệu đó vẽ thành biểu đồ Dashboard ngầu đét.

1. Prometheus (Kẻ thu thập - Time-Series DB)

Prometheus hoạt động theo cơ chế PULL. Nghĩa là cứ mỗi 15 giây, nó lại phi tới Database của bạn để "hút" dữ liệu các chỉ số về. Để nó hút được DB, bạn phải cài một cái đầu hút gọi là Exporter (VD: mysqld_exporter hoặc postgres_exporter).

Dữ liệu lưu dạng Chuỗi Thời Gian: tên_chỉ_số{nhãn="a"} giá_trị timestamp

2. Grafana (Hiển thị UI & Cảnh báo)

Grafana móc nguồn vào Prometheus, dùng ngôn ngữ PromQL để vẽ biểu đồ.

Tip cho dân Lười: Lên Thư viện Grafana, search "MySQL Exporter" (VD ID: 7362), paste vào Grafana là có ngay Dashboard ngầu đét. Thêm chức năng Alerting: Gửi tin nhắn Telegram/Slack nếu CPU DB vượt quá 90%.

// PromQL: Các câu truy vấn Sống còn cho Database

1. Đếm số lượng Query chậm (Slow Queries) sinh ra MỖI GIÂY (QPS) trong vòng 5 phút qua

rate(mysql_global_status_slow_queries[5m])

-> Nếu biểu đồ cột này > 0 và tăng dựng đứng, DB của bạn đang kẹt cứng (Missing Index / Lock).

2. Số lượng Connection đang MỞ và chiếm dụng

mysql_global_status_threads_connected

-> Trạm max_connections thì App sập (Thường do lập trình viên quên đóng kết nối Pool).

3. Tính % Tỉ lệ Cache Hit của Redis (Tuyệt chiêu)

rate(redis_keyspace_hits_total[5m]) / (rate(redis_keyspace_hits_total[5m]) + rate(redis_keyspace_misses_total[5m])) * 100

-> Nếu % Hit Rate < 50%, Redis của bạn vô dụng, Backend đang chọc thủng Cache xuống DB quá nhiều.

🚨 Khi DB có biến, hãy nhìn vào 3 biểu đồ này đầu tiên:

  • Disk IOPS / Disk Wait: Tốc độ Đọc/Ghi ổ cứng. Database là trùm ngốn ổ cứng. Nếu Disk Wait quá cao, nâng cấp CPU cũng vô dụng, bạn phải đổi sang ổ SSD xịn hơn hoặc bắt đầu chia nhỏ DB (Sharding).
  • Replication Lag (Trễ đồng bộ): Khi bạn chạy 1 Master (Ghi) và nhiều Slave (Đọc). Nếu Slave đồng bộ chậm 5s -> User vừa thêm vào giỏ hàng xong, F5 lại giỏ hàng thấy biến mất (vì hệ thống lỡ đọc ở con Slave chưa đồng bộ xong).
  • Connection / Thread Pool: Đường ống nối vào DB bị nghẽn.

Message Queue: Apache Kafka & Lầm tưởng thú vị

Khi hệ thống lớn, các Microservices không nên gọi HTTP trực tiếp cho nhau (nếu một thằng chết, cả đám chờ mòn mỏi). Ta dùng "Hộp thư bưu điện" đứng ở giữa. Thằng A thả thư vào Hộp, thằng B rảnh rỗi mới tới lấy thư đọc (Bất đồng bộ - Asynchronous).

Captcha vs Kafka?

Có vẻ như bạn đang nghe nhầm hoặc gõ nhầm. Hai khái niệm này nằm ở 2 thái cực hoàn toàn khác nhau:

  • CAPTCHA: (Mã chống Bot). Cái ô đánh dấu "I'm not a robot" ở giao diện FE. Nó không liên quan gì đến DB/Backend System Design.
  • Apache Kafka: (Có thể bạn gõ nhầm "Apache" thành Capcha). Là hệ thống xử lý Event/Message khổng lồ. Hoặc bạn muốn so sánh Kafka với RabbitMQ (một Message Broker rất nổi tiếng).

# Tư duy Kiến trúc Apache Kafka

Khái niệm cốt lõi

  • 📬 Topic (Chủ đề): Giống như cái ống nước. Service A bắn sự kiện order_created vào ống này.
  • 📦 Partition (Phân vùng): 1 Topic chia ra thành nhiều Partition nhỏ để chạy song song (Scale ngang). Kafka lưu data trực tiếp trên Ổ cứng HDD thành các file Log liên tiếp.
  • 👷 Producer / Consumer: Người bắn tin nhắn / Người đọc tin nhắn.
  • 🔖 Offset: Dấu trang (Bookmark). Consumer đọc tới dòng 100 thì đánh dấu Offset=100. Tắt máy mở lại, nó đọc tiếp từ 101.

Kafka vs RabbitMQ

Nếu nãy giờ bạn định so sánh 2 ông trùm này, thì đây là sự khác biệt lớn nhất:

  • RabbitMQ (Smart Broker, Dumb Consumer): Hàng đợi thông minh. Thằng gửi gửi thư, RabbitMQ chủ động dí thư vào mặt thằng nhận. Nhận xong, thư bị XÓA NGAY LẬP TỨC khỏi bộ nhớ. Rất tốt cho hệ thống Transactional, Task queue, gửi Email.
  • Apache Kafka (Dumb Broker, Smart Consumer): Hàng đợi ngu ngốc. Kafka chỉ lưu tin nhắn vào ổ cứng (giữ đó 7 ngày không xóa). Các Consumer phải TỰ VÁC MẶT TỚI ĐỌC (Pull) và tự nhớ vị trí đọc. Siêu nhanh, xử lý hàng triệu data/giây, dùng cho BigData, Tracking User Action, Log.
